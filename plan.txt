## Full MAX Auth codebase audit — 2026-11-17

### Authentication, session and account lifecycle
- Fixed Zod 4 TypeScript compatibility issues in validation middleware and admin status validators.
- Authentication middleware now distinguishes invalid JWTs from database/infrastructure failures; database outages are no longer misreported as invalid credentials.
- JWT session authentication avoids an unnecessary OAuth introspection lookup; internal introspection and OPTIONS traffic are excluded from usage telemetry.
- CSRF token derivation no longer depends on client IP, avoiding invalidation when users change networks. Refresh requests also validate browser Origin against configured and first-party MAX origins to protect the SameSite cookie across sibling subdomains.
- Refresh cookies are cleared after password reset/change, logout, current-session revocation, current-device revocation, and revoke-all-sessions.
- Device and session listing queries now select only safe fields; refresh-token hashes and device fingerprints are not returned to account clients.
- Admin suspension now atomically revokes first-party sessions, OAuth access/refresh tokens, authorization codes, consents, and pending password-reset tokens. Deleted accounts cannot be reactivated; parental-consent-pending accounts cannot be promoted to active by the normal admin reactivation flow.
- Parental approval now atomically checks the child is still pending and, for account-based approval, requires an active account with a verified matching guardian email. Accounts that have their own parental-consent record cannot act as guardians. The email-link path still relies on mailbox possession and explicit guardian attestation; it does not independently prove age or legal guardianship.
- Business invitations now require the invited MAX Account to be active and email-verified before acceptance.

### OAuth and connected-account security
- Added connectedAccountLink.service.ts and migrated Google, Spotify, Discord, Microsoft, GitHub, Instagram, TikTok, and X callbacks to race-safe identity linking. A unique-key race can no longer overwrite another MAX Account's provider identity ownership. Regression tests cover existing-owner and concurrent-create cases.
- OAuth redirect URI validation now rejects hostname-prefix localhost bypasses, non-local HTTP callbacks, credentials, fragments, and dangerous schemes. Existing stored redirect URIs are revalidated during authorization, approval, and code exchange.
- OAuth authorized origins now require a clean origin and HTTPS except exact localhost/loopback development origins. OAuth manifest URL fetches reject private/reserved IPs, pin DNS results, reject redirects/credentials, enforce JSON content type, a 256 KB response cap and a timeout; redirect URI manifest checks reject duplicates and require an exact set match.
- Fixed OAuth client logo SQL column names for the camelCase oauth_clients schema and changed non-returning UPDATE statements from $queryRawUnsafe to $executeRawUnsafe. Logo uploads now validate PNG/JPEG/WebP file signatures and public logo responses set X-Content-Type-Options: nosniff.
- OAuth client tester now includes reserved MAX system-client scopes.
- System OAuth client bootstrap no longer reactivates a client disabled by an administrator; concurrent startup creation is handled safely and dummy client secrets use cryptographic randomness.
- Business legal-identity changes (legal/display name, address, country, business type, registration number) reset verification to PENDING, invalidating business OAuth introspection until re-review.
- External Google, Spotify, Discord, Microsoft, GitHub, Instagram, TikTok, X and Resend requests now have bounded timeouts.

### Webhooks and external requests
- Webhook secrets are encrypted at rest and the raw secret returned to the owner is used for HMAC signatures; legacy hash-key records remain compatible until rotated.
- Webhook delivery rejects private/reserved destinations, pins validated DNS answers to the HTTPS connection to prevent DNS rebinding, rejects redirects, and catches decryption failures without terminating the retry worker.
- Production now requires a stable dedicated WEBHOOK_ENCRYPTION_KEY (at least 32 bytes).

Missing requirements will stop startup rather than silently disable critical auth/email/OIDC functions.

- Email API requests now have a 10-second timeout and bounded error-body logging.

- Continued the Connected Apps backend follow-up after frontend PR #33 shipped.
- Confirmed the backend already persists CONNECTED / REAUTH_REQUIRED and retains linked-account rows when refresh credentials are rejected. The remaining classification defect was that refresh handlers inferred revocation from broad message text such as "unauthorized" or "refresh token", which could misclassify unrelated provider failures.

## 2026-11-25 — MAX Chat connected-account OAuth authentication repair
- Root cause confirmed from source: MAX Chat uses opaque OAuth access tokens issued by `oauthService.exchangeCode()`, while `src/routes/connectedAccounts.routes.ts` applied the first-party `authenticate` middleware, which calls `verifyAccessToken()` and expects a JWT. Connection-start and mutating requests additionally require the already-approved `profile:write` permission.
