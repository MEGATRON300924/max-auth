## Current task: Prevent concurrent refresh-token requests from revoking MAX sessions (2026-11-17)

### Root cause
- `rotateRefreshToken` treated every already-revoked refresh session as token theft and immediately revoked all sessions for that user.
- The MAX refresh cookie is host-only on `auth.max-ai.name.ng` and shared by first-party MAX products. Separate tabs and product origins have independent JavaScript refresh promises and can submit the same cookie concurrently.
- A winning request rotates the token; concurrent requests then see the old session as revoked and trigger account-wide session revocation. Repeated 401/recovery attempts can then exhaust the global API rate limit.

### Implementation on `fix/refresh-token-concurrency`
- Added a 15-second concurrency grace window based on the old session's `revokedAt`.
- A recently rotated token now returns HTTP 409 with `REFRESH_TOKEN_ROTATED`, allowing the client to retry after the winning response updates the shared cookie.
- The conditional-update race path re-reads the session and applies the same grace rule.
- Refresh-token reuse outside the short grace window still triggers account-wide session revocation as a security response.
- No rate limits were increased and refresh-token reuse detection was not disabled.
