## Current task: Prevent concurrent refresh-token requests from revoking MAX sessions (2026-11-17)

### Root cause
- `rotateRefreshToken` treated every already-revoked refresh session as token theft and immediately revoked all sessions for that user.
- The MAX refresh cookie is host-only on `auth.max-ai.name.ng` and shared by first-party MAX products. Separate tabs and product origins have independent JavaScript refresh promises and can submit the same cookie concurrently.
- A winning request rotates the token; concurrent requests then see the old session as revoked and trigger account-wide session revocation. Repeated 401/recovery attempts can then exhaust the global API rate limit.

### Implementation on `fix/refresh-token-concurrency`
- Added a 5-second concurrency grace window based on the old session's `revokedAt`, keeping the collision recovery window short.
- A recently rotated token now returns HTTP 409 with `REFRESH_TOKEN_ROTATED`, allowing the client to retry after the winning response updates the shared cookie.
- The conditional-update race path re-reads the session and applies the same grace rule.
- Refresh-token reuse outside the short grace window still triggers account-wide session revocation as a security response.
- No rate limits were increased and refresh-token reuse detection was not disabled.

### Verification
- Source review completed for both refresh race paths.
- Build, tests, GitHub Actions and live concurrent-refresh integration test: pending.
- No deployment or merge performed.

## MAX Backend session validation failure — service introspection rate limit — 2026-11-17
- Investigated the live MAX Chat error "MAX Auth could not validate this session" using Render logs from max-backend service `srv-d7eeuc0sfn5c738tml3g`.
- The failing request was POST `/api/v1/conversations/:id/messages/stream`; `requireAuth` failed before Gemini execution while calling MAX Auth `POST /api/v1/oauth/introspect`. The backend currently maps every non-2xx introspection response to generic `AUTH_SERVICE_ERROR` / HTTP 503, so the exact upstream status is not preserved in the log.
- Nearby authenticated GET conversation requests returned HTTP 200, then the stream request failed with 503. CORS was correct for `https://chat.max-ai.name.ng`; this is not a CORS failure.
- MAX Auth Render logs also showed a burst of repeated `No refresh token provided` warnings. The global MAX Auth rate limiter is applied before all `/api/v1` routes and defaults to 100 requests per 15 minutes. The trusted server-to-server introspection endpoint was therefore sharing the public browser/API IP budget despite already requiring the secret `X-MAX-Service-Token`.
- On branch `fix/service-introspection-rate-limit`, changed `globalRateLimiter` to skip only POST `/api/v1/oauth/introspect`. The endpoint still enforces `MAX_AUTH_SERVICE_TOKEN` in `oauthController.introspect`; no other route or rate limit is bypassed.
- This addresses a concrete rate-limit design flaw that can reject legitimate backend session checks. The precise upstream status for the user's failed request remains unconfirmed because the backend middleware does not currently log the upstream status/body code.
- Next: run MAX Auth CI/build, open PR, merge only after checks pass, deploy and retest MAX Chat. If the issue persists, improve backend introspection diagnostics to record sanitized upstream status/error code (never token or service-token values). MAX Backend Gemini-only deployment remains live; Botpress untouched.
